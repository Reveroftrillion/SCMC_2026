# 개인 Codex 개발 계획과 인계

2026-10-13 기준. 개인이 Codex로 개발하며 과거 3팀 분담을 현재 조직으로 사용하지 않는다.
[저장소 규칙](../../AGENTS.md), [문서 분류](MARKDOWN_INDEX.md), [실제 실행 안내](../README.md)를 함께 사용한다.
이 문서는 현재 계획이며 날짜별 검증 기록의 수치·작성자·결론을 다시 쓰지 않는다.

수동 실행의 출력 축소 명령과 최근 터널 정지/재기동 구분은
[터미널·터널 재확인](CONSOLE_TUNNEL_RECHECK_2026-10-22.md)을 확인한다.
`bash ros1-port/docker/run_course.sh drive:=true bag:=true`는 화면 반복만
줄이고 새 폴더에 원문·센서 기록을 남긴다. 시작점 전용이며 자동 종료 감독은 없다.

2026-10-22 최신 수정은 [오른쪽 정적·보행자 기록](RIGHT_STATIC_PEDESTRIAN_2026-10-22.md)을
확인한다. 정적 경로를 오른쪽으로 바꾸고 보행자 구간의 지면 높이 기준을
보정했으며 원본 연속 입력으로 검증했다. 이 수정본의 실제 MORAI 주행은
아직 수행하지 않았다. 아래 완주는 이전 왼쪽 회피·보행자 수정 전 버전의 결과다.

2026-10-22 실제 시험 결과는 [전체 코스 기록](FULL_COURSE_AUDIT_2026-10-22.md)을
먼저 확인한다. 같은 sample_scene에서 정적 우회·전체 CP·터널 GPS→DR→GPS·
END/FINISH를 실제 한 번 통과했고 정지·Manual/P를 확인했다. 첫 랩 시작점
오투영을 피하는 명시적 `start_at_beginning` 옵션과 이번 시험 launch 사본의
재현 명령은 해당 문서에 있다(기본값false). 다음 우선순위는 최신 수정본의
오른쪽 회피·보행자 양보/재출발 실제 검증과 조건을 바꾼 반복 시험이다. 전체 코스
통과와 모든 미션 의미/공식 채점 검증은 구분한다.

## 1. 전체 구조

독립 catkin 워크스페이스에 원본 7개 패키지와 `foscar_ros1` 어댑터가 있다.
원본은 `2026foscar-competition/`이며 실행 어댑터가 ROS2 형태의 호출을 ROS1 `rospy` 경계로 연결한다.

| 구성 | 입력 → 역할 → 출력 |
| --- | --- |
| `foscar_interfaces` | VehicleStatus, ControlCommand, DrivingTarget 등 ROS 메시지 생성 |
| `foscar_bringup` | ROS1 XML launch, 지도·경로·설정, 노드 실행·종료와 bag 구성 |
| `foscar_control` | GPS/IMU/Competition UDP → sensor_bridge → localization(GPS/DR, s, TF); DrivingTarget → path_follower → ControlCommand → bridge UDP 송신 |
| `foscar_camera` | Camera-7 UDP JPEG → camera_bridge → YOLO box → ROI 색 선택·프레임 확정 → traffic_signal |
| `foscar_lidar` | VLP16 → cloud → 좌표 변환·도로 필터·군집·추적 → 이벤트·footprint·road_users |
| `foscar_planning` | 위치·인지·미션 → Behavior와 신호 기억·상태 제약 합성 → DrivingTarget 단일 발행 |
| `foscar_camera_train` | 수집·라벨·학습 보조 도구. 대회 runtime과 별도이며 offline ROS2 launch의 ROS1 실행은 미검증 |
| `foscar_ros1` | publisher/subscriber, callback group, 큐·executor·timer, ROS time, parameter, 메시지 기본값·PointCloud2 경계 |

```mermaid
flowchart LR
  Sensors[GPS·IMU·Status] --> Bridge[sensor_bridge]
  Bridge --> Pose[localization·TF·s]
  Camera[Camera-7] --> YOLO[camera_bridge·YOLO·ROI]
  Lidar[VLP16] --> Objects[lidar_bridge·obstacle_node]
  Pose --> Behavior[Behavior·미션·SignalStopPolicy]
  YOLO --> Behavior
  Objects --> Behavior
  Behavior --> Target[DrivingTarget]
  Target --> Follower[path_follower]
  Pose --> Follower
  Follower --> Bridge
  Bridge --> MORAI[제어 UDP9093: drive=true일 때]
```

후륜축 경로 진행거리 `/localization/s`와 앞축 기준 `DrivingTarget.stop_s`를 구분한다.
`drive:=false`에서도 ROS 제어 요청은 생성될 수 있으며 실제 UDP 송신 여부는 bridge에서 결정한다.
구체적인 미션 범위·ROI·계산식은 [ROS1 README](../README.md)의 구현 설명과 실제 JSON/YAML을 대조한다.

## 4. 우선순위와 신호 문제 조사 순서

1. **P0: 두 번째 교차로 녹색 미채택 원인 규명.** 처음에는 Ubuntu에서 `drive:=false`로 관측한다. 실제 주행은 별도 명시 지시 후 수행한다.
2. **P1: 원인에 따른 별도 수정.** 목표·영향 파일·구현·검증·완료 기준을 먼저 기록하고, 동작 변경 요청 범위에서만 수행한다. 이번 이름/문서 정리에 포함하지 않는다.
3. **P2: 센서 조건·좌표 기준, 종료 traceback 및 bag/YOLO 로그 보존 검증.** 원본 설정과 현장값의 출처를 명시한다.
4. **P3: 실제 ROS 시간·큐·전송 검증과 전체 미션 replay/주행.** clock pause/rewind/jump, callback 동시성·overflow, TCPROS 지연·손실·재연결·과부하 및 ROS2 비교를 포함한다.

P0에서는 같은 교차로 ID와 stamp로 아래 경계를 순서대로 비교한다.

| 순서 | 관측·판단 기준 | 실패 시 조사 |
| --- | --- | --- |
| 1. Camera-7 영상 | 따라야 할 방향의 녹색이 실제 JPEG 안에 있는가? 센서ID·해상도·pitch·FOV 기록 | 카메라 입력/preset. MORAI 전체 화면과 JPEG를 동일시하지 않음 |
| 2. YOLO box | 같은 저장 영상에서 원본/이식 Detector의 box·color·confidence 비교 | 녹색 누락/빨강 오분류/다른 방향 신호와 모델 입력 조건 |
| 3. ROI | box 중심 normalized x/y가 intersection_02 ROI `[0,0,0.9,1]` 안인가? 다른 색이 함께 있는가? | ROI 밖 중심·모순 색. 먼저 threshold를 낮추지 않음 |
| 4. 신호 선택 | chosen과 연속2처리프레임, `/perception/traffic_signal`의 id/color/stamp 대조 | gate/s freshness, epoch·교차로 전환, 추론 후 age, 노드 오류 |
| 5. Behavior | 현재교차로와 허용색, age[-0.05,1.0], 새로운 stamp, reset 및 GO/STOP 확인 | 전달·기억 갱신 순서. 녹색 이후 미검출 기억 정책 보존 |
| 6. DrivingTarget | `/behavior/target` state/v_max/stop_s와 signal_stop을 대조 | GO 이후에도 AVOID/YIELD 등 독립 제약이 있는지 확인 |
| 7. 후속 제어 | target stamp/timeout, odom/status, mode2/gear4, watchdog, 실제 송신과 Pause 확인 | 사용자 허용 주행에서만 실제 출발 연결 확인 |

같은 영상에서 양쪽 Detector가 같은 잘못된 결과면 입력/원본 모델·ROI 문제 후보이며, 서로 다른 결과면 이식 경계·라이브러리를 조사한다.
모의 녹색 발행, 기억 삭제, watchdog/timeout 해제로 성공 판정을 만들지 않는다.

## 6. Ubuntu MORAI PC 검증

Windows Python 환경과 Ubuntu ROS 환경을 혼용하지 않는다. 현장 경로는 `/home/foscar/RMT-ros1`, 이미지 `rmt-noetic-py310:local`이다.
호스트 Ubuntu20.04의 Python3.8 Noetic 대신 Docker Ubuntu22.04/Python3.10 Noetic underlay를 사용한다.
Linux host network와 NVIDIA runtime을 사용하며 Competition `127.0.0.1:9088→127.0.0.1:909`, 제어 수신9093, Camera-7 수신9297 설정을 보존한다.

[실행·종료·네트워크 안내](../README.md#2026-10-13-morai-실행과-다음-작업-인계)에 따라 포트 점유와 Competition 별도 Connect를 확인한다.
기존 launch가 없는 상태에서만 수신용 probe 또는 다음 launch 하나를 사용한다. 이 문서 작성 중에는 실행하지 않았다.

```bash
cd /home/foscar/RMT-ros1
bash ros1-port/docker/run.sh --receive-root \
  roslaunch docker/local.launch drive:=false bag:=true
```

별도 터미널에서 기존 master의 정책·목표를 확인한다.

```bash
bash ros1-port/docker/run.sh rostopic echo /perception/traffic_signal
# 앞 명령을 Ctrl+C로 끝내거나 각각 별도 터미널에서 실행한다.
bash ros1-port/docker/run.sh rostopic echo /behavior/signal_stop
bash ros1-port/docker/run.sh rostopic echo /behavior/target
```

기본 bag의 raw/debug 영상 누락을 반복하지 않도록 필요한 토픽을 추가 기록한다.

```bash
rmt_diag_id=$(date +%Y%m%d-%H%M%S)
mkdir -p ros1-port/docker/artifacts/signal-diagnostics
bash ros1-port/docker/run.sh rosbag record \
  -O "/workspace/ros1-port/docker/artifacts/signal-diagnostics/${rmt_diag_id}.bag" \
  /sensors/camera/traffic/compressed /perception/traffic_light/debug/compressed \
  /perception/traffic_signal /behavior/signal_camera /behavior/signal_stop \
  /behavior/target /behavior/mission /control/request /control/state \
  /control/telemetry /vehicle/status /localization/odometry /localization/s \
  /localization/mode /tf /tf_static
```

YOLO JSONL의 line/s/stamp/infer_ms/chosen/dets도 호스트에 남기는 [기존 기록 경로 설정](../README.md#다음-재현에서는-원본-영상과-검출-로그를-호스트에-남긴다)을 적용한다.
닫힌 bag을 실제로 열어 raw/debug 프레임과 신호·목표가 같은 시각에 있는지 확인한다. drive=false에서는 제어 UDP0을 다시 확인한다.
사용자가 별도 지시한 주행에서만 녹색→GO→신호 제약 해제→출발과 Ctrl+C 제동·Manual/P·실제 속도0을 확인한다.
빨강/노랑 정지, 다른 방향 신호, 미검출 기억, 독립 장애물 정지, 4번 좌회전도 회귀 검증한다.

## 7. 완료 판단 기준

- 식별자 정리: 공개 인터페이스·문자열·상수·계산·분기·실행 순서가 보존되고, 93개 이름 역매핑 AST 일치 및 실행 가능한 회귀 검사가 통과한다. 기존 바이트 검사 실패는 파일별 의도된 차이와 대조한다.
- 문서 정리: 현재 계획·과거 팀 문서·검증 근거가 구분되고 내부 링크/실행 경로가 유효하다. 보호 기록·JSON·manifest와 원본에 변경이 없다.
- **신호 버그는 아직 완료 아님:** 재현 영상으로 원인 경계를 확인하고 별도 수정 후 같은 교차로의 녹색 채택→GO→DrivingTarget 신호 제약 해제를 입증한다. 실제 출발 검증은 사용자 승인 시험 결과가 추가로 필요하다.
- 전체 이식 완료는 별도 판단한다. 짧은 주행·합성 영상·Windows 테스트 성공만으로 전체 미션 및 전송 동등성을 완료 처리하지 않는다.

## 8. Git 브랜치와 커밋

기준은 `feat/ros1-port`, 이번 작업은 `refactor/identifiers-docs`다. 새 버그 수정은 목적별 `fix/...`, 검증은 `test/...` 등 별도 브랜치로 구분한다.
변경 전 상태를 확인하고 코드 정리와 문서·검증 도구를 검토 가능한 단위로 커밋한다. 이번 세션은 커밋/push/main 병합을 수행하지 않는다.
커밋 시 실제 변경 파일을 명시해 스테이징하고 `git diff --cached --stat`, `git diff --cached --check`로 확인한다.
GitHub push와 main 병합은 별도 지시가 있을 때만 수행한다. 2026-10-13 이전 마감의 push 승인을 재사용하지 않는다.

## 9. 작업별 변경 이력

새 문서나 새 날짜/작업별 기록에 아래 항목을 작성하고 기존 검증 기록은 보존한다.

```text
날짜(KST) / 작업 브랜치 / 기준 커밋:
개발 목표 / 영향 파일:
구현 방법 / 보존한 외부 계약 / 보류한 항목:
재현 조건 / 실행 명령 / interpreter·환경:
검증 결과(PASS·FAIL·skip·미실행) / 새 artifact 경로:
완료 기준 충족 여부 / 남은 문제:
```

실험마다 입력·stamp·센서 preset·source commit·출력 경로를 남긴다. 최초 실패와 재실행을 구분하며 과거 수치에 새 결과를 덮어쓰지 않는다.
