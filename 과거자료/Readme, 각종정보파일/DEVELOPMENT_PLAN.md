# 모듈형 자율주행 개발 계획

작성일: 2026-09-08. 상태: 자료 검토 기반 1차 계획, 환경·포트·공식 원본·팀 일정 답변 대기.
이번 범위는 설계와 작업 분담이다. 실행 코드 구현이나 시뮬레이터 제어 송신은 수행하지 않는다.

## 1. 목표와 첫 버전의 범위

기본 주행 스택을 먼저 안정화하고, 같은 입출력 계약에 미션 기능을 추가한다.
여기서 '기본 주행 모델'은 우선 학습 모델이 아니라 위치 추정·경로 추종·속도 제어를 포함하는 실행 기반으로 해석한다.

- 첫 버전: 허용 UDP 수신 → 위치 추정 → 지정 경로 → Pure Pursuit 횡제어 + PID 종제어 → 제어 UDP 송신.
- 포함: 출발 모드/기어 전환 확인, 정지 유지, 입력 유효성 검사, 명령 만료 처리, 기록·재생, 설정 분리.
- 첫 시연: GPS 정상·장애물 없는 시험 구간에서 10~15 km/h로 출발, 직선/곡선 추종, 지정 지점 정지.
- 확장: 신호·보행자·정적 장애물·끼어들기·회전교차로·터널 위치 추정·터널 랜덤 미션.
- 기본 주행 시연과 대회 전체 완주는 별도 완료 기준이다. 첫 버전으로 미션이 있는 코스를 무조건 주행하지 않는다.

## 2. 자료에서 확인한 사실과 확인이 필요한 주장

| 자료 | 확인 결과 | 계획에 반영 |
|---|---|---|
| PROJECT_MASTER.md | 대회 규정/미션/스택/진행 상태를 정리한 2차 문서 | 규정 관련 내용은 원본 확보 후 대조 |
| Readme.txt | Competition Status 제외 필드, 공식 참고 저장소, 포트 안내 | 전체 Ego Status를 위치 입력으로 가정하지 않음 |

| 카메라 JSON 기타 센서 | GPS/IMU/LiDAR 목록이 비어 있음 | 이 파일만으로 전체 센서 구성 불가 |
| morai_re_analysis | 내장 제어 분석 HTML, IL 덤프 2개, 분석 스크립트 | 참고 분석이며 UDP 명세나 검증된 팀 제어기로 취급하지 않음 |

IL 덤프는 구조와 HTML의 주요 근거 메서드 #203/#363/#420/#644를 선별 대조했다.
덤프 전체의 의미나 내장 로직의 실제 호출 경로를 검증한 것은 아니다.

현재 없는 자료: 공식 전역경로 TXT, 샘플 시나리오 JSON, 규정집 v1.1 원본, 최신 Q&A/점검 가이드,
전체 센서 설정, 차선 경계/신호/정지선 등 추가 MGeo 파일.
global_info의 해시 목록에 파일명이 있어도 실제 파일이 제공된 것은 아니다.
맵 전체 링크와 대회가 지정한 링크 순서는 다르므로 체크포인트 사이 최단경로를 공식 경로로 확정하지 않는다.
2,184.6m/4,430점과 미션별 진행거리도 공식 경로 확보 전에는 종합 문서의 참고값이다.

설계상 정정 사항:

- 위치 필드가 없다는 사실이 EKF 사용을 강제하지는 않는다. GPS/IMU 직접 보정과 속도 기반 예측으로 시작 가능하다.
- 차량 제원 부족은 운동학 모델을 우선할 이유지만 동역학 모델이 원천적으로 불가능하다는 뜻은 아니다.
- 전 센서 무노이즈라고 해도 압축, 양자화, 지연, 좌표 오차, 가림, 오인식은 남는다.
- Competition Status에는 위치가 없으므로 재배치 후 실제 위치 확인은 GPS 또는 위치 추정기로 한다.
- 내장 로직에서 보이는 조향 부호/기어 숫자를 외부 UDP 규약으로 그대로 가져오지 않는다.
- 맵 max_speed에 80 등 값이 있어도 대회 제한속도를 대신하지 않는다. 대회 규정 레이어를 별도로 둔다.

## 3. 통신 구조

```text
시뮬레이터 PC 192.168.10.1
  ├─ 허용 상태/센서 UDP ─→ 알고리즘 PC <IP 확인 필요>
  └─ Ego Ctrl Cmd UDP  ←─ 최종 송신기 단일 프로세스

알고리즘 PC 내부
  UDP 브리지 → ROS2 토픽 → 위치 추정 / 카메라 / 라이다
                               ↓
  지정 경로·미션 지도 → 판단·지역경로·속도계획
                               ↓
                         경로·속도 제어
                               ↓
                    명령 검사·watchdog·UDP 송신
```

종합 문서의 순수 UDP 제약을 잠정 요구사항으로 적용한다. ROS2는 알고리즘 PC 내부 모듈 연결에 사용한다.
기본 실행은 알고리즘 PC 한 대에서 수행하고, 7명은 패키지를 나누어 개발한다.

| 채널 | 방향 | 현재 정보 |
|---|---|---|
| Ego Ctrl Cmd | 알고리즘 → 192.168.10.1 | 시뮬레이터 수신 포트 미확인 |
| Competition Vehicle Status | 시뮬레이터 → 알고리즘 | 9099 수신 성공 기록, 현재 상태 재확인 |
| CollisionData | 시뮬레이터 → 알고리즘 | 9091 수신 성공 기록, 현재 상태 재확인 |
| Camera 1/2/3 | 시뮬레이터 → 알고리즘 | 설정 파일 목적지 9291/9293/9295 |
| GPS / IMU / LiDAR | 시뮬레이터 → 알고리즘 | 포트·설정·장착 pose 미확인 |

192.168.10.1은 송신 목적지이며 알고리즘 PC의 로컬 bind 주소가 아니다.
IP/목적지 포트/로컬 포트/인터페이스를 설정으로 분리하고, 포트별 프로세스 소유자를 한 명으로 정한다.
종합 문서의 알고리즘 PC 주소 192.168.10.2는 사용자 확인 전 잠정값이다.

브리지 구현 전 패킷 계약으로 확정할 항목:

- 헤더, 전체/페이로드 길이, 필드 오프셋, 자료형, endian, 단위, 결측 표현.
- Competition Status의 축소 필드 배치: 일반 Ego 예제에서 필드를 삭제한 것으로 추정해 파싱하지 않는다.
- 제어 cmd type=1, ctrl mode=2는 문서 기준 잠정값. 기어 코드, 조향 부호·단위·범위는 명세와 실측으로 확정.
- 카메라 프레임 분할·순서 뒤바뀜·유실·조립 만료, LiDAR 패킷 형식 및 스캔 조립.
- 송신 성공은 send 호출 반환으로 판정하지 않고 허용 상태 피드백과 차량 반응으로 확인.

허용 채널만 구독하고 기록한다. 대용량 영상 처리와 제어 송신은 실행 경로를 분리한다.
최종 송신기는 오래된 제어 명령을 반복하지 않고 만료 시 감속/정지 명령으로 전환한다.
송신기나 네트워크 자체가 죽으면 정지 UDP 도달은 보장되지 않으므로 시뮬레이터의 통신 단절 반응도 시험한다.

## 4. 모듈 계약: 팀 개발 전에 고정할 것

내부 단위는 m, s, m/s, rad. map은 ENU, base_link는 후륜축 중심을 잠정 기준으로 두고 원본과 실측으로 확인한다.
센서 장착 좌표의 기준점과 축 방향을 확인한 뒤 base_link→각 센서 변환을 등록한다.
모든 시간 데이터는 공통 시계 기준, 수신 시각, 유효 상태를 가진다. 센서 시각이 없다면 생성 시각처럼 꾸미지 않는다.
명령 만료와 watchdog 경과시간은 단조 시계를 사용한다. 재생 시에는 재생 시계와 명령 송신 금지를 적용한다.

| 출력/토픽 초안 | 생산자 → 소비자 | 필수 의미 |
|---|---|---|
| /sensors/gps, /sensors/imu | 센서 브리지 → 위치 추정 | 측정값, frame, 시각, fix/valid 상태 |
| /vehicle/status | 통신 → 위치 추정·제어·송신기 | 종속도, 기어/모드 피드백, 데이터 유효성 |
| /sensors/camera/*, /sensors/lidar | 센서 브리지 → 인식 | 이미지/점군, frame, 시각 |
| /localization/odometry + health | 위치 추정 → 계획·제어 | pose/twist, 불확실성, GPS/예측/보정 상태 |
| /map/route + route_progress | 맵 → 계획 | route_id, 순서 있는 경로, link_id, 진행거리 s, 체크포인트 |
| /perception/traffic_signals | 카메라 → 판단 | 관측 신호, confidence, 관련 신호/차로 연결 상태 |
| /perception/lanes | 카메라 → 계획·위치 추정 | 차선 기하, 관측 범위, confidence |
| /perception/objects | 라이다 → 판단·계획 | track_id, 크기/위치/속도, frame, 불확실성 |
| /localization/lidar_correction | 라이다 → 위치 추정 | 보정치, 관측 가능한 방향, confidence |
| /planning/constraints | 미션 판단 → 계획 | 속도 상한, 정지 위치, 주행 가능 영역, 사유, 만료시각 |
| /planning/trajectory | 계획 → 제어 | 순서 있는 pose와 목표속도, frame, 생성·만료시각 |
| /control/request | 제어 → 최종 송신기 | 페달 요구, 내부 조향각 rad, 정지/기어 요청, 만료시각 |
| /system/health | 모든 모듈 → 통합·송신기 | heartbeat, 입력 age, 실패 사유 |

메시지 상세 타입은 환경 확정 후 정한다. 표준 센서/경로 메시지를 우선하고 추가 의미만 팀 메시지로 정의한다.
UDP 단위·부호·정규화 변환은 브리지 경계에서만 수행한다.
센서 스트림은 최신값 중심의 작은 큐, 경로/설정은 늦게 시작한 구독자도 받도록 설계한다.
QoS와 큐 크기, 주기·만료 임계값을 interfaces 문서에 함께 명시한다.

미션 모듈은 직접 UDP를 보내지 않는다. 최종 trajectory 발행자는 계획 모듈 하나,
최종 제어 송신자는 송신기 하나로 제한한다. 다른 제어기를 실험할 때도 선택된 하나만 명령을 발행한다.

동시 미션 처리 예: 신호 정지 요구와 장애물 회피 요구를 함께 받는다.
주행 가능 영역 안에서 정지선을 지키는 경로를 계획하며, 충돌 없는 해가 없으면 정지한다.
속도 상한은 활성 제약 중 최소값을 사용하되, 정지선과 장애물 위치는 경로 전체에 반영한다.
단순히 '현재 미션 하나'를 선택하는 상태기로 동시 요구를 버리지 않는다.

## 5. 기본 주행과 확장 순서

1. 위치 추정: 유효 GPS→UTM→로컬 좌표, IMU 헤딩, 상태 속도로 시작한다. 센서 lever arm과 yaw 부호를 검증한다.
2. 경로: 공식 순서·방향을 유지하고 진행도 주변에서 매칭한다. 교차로나 순환 시작점에서 최근접점이 다른 구간으로 점프하지 않게 한다.
3. 기본 계획: 전역 경로 일부를 지역 경로로 내보내고 곡률·정지 거리·설정 속도에 따른 속도 프로파일을 생성한다.
4. 제어: Pure Pursuit + 속도 PID, 적분 포화 방지, 조향/페달 한계, 정지 유지. lookahead와 감속 성능은 저속부터 실측한다.
5. 출발: INIT→입력/위치 확인→정지 유지→Auto/D 요청→상태 확인→READY→DRIVING. 실패 시 주행으로 넘어가지 않는다.
6. 신호·보행자 정지: 먼저 인식→정지→재출발을 완성한다. 신호 UNKNOWN과 오래된 인식은 정상 진행 허가로 취급하지 않는다.
7. 정적 회피: 주행 가능 영역 내 후보 경로와 차량 크기로 충돌 검사 후 원래 경로에 복귀한다.
8. 동적 객체: 추적과 상대속도로 양보/정지/진행을 결정하고 회전교차로와 끼어들기에 적용한다.
9. 터널: GPS 부재는 정상적인 미션 상태로 분리한다. IMU+속도 예측, 라이다/차선 보정을 같은 odometry 출력에 추가한다.
10. 전체 통합: 터널에서 위치 추정과 장애물 회피가 동시에 작동하는지 확인한다.

평행한 터널 벽은 횡위치/방향 보정에는 도움이 되지만 종방향 위치까지 항상 관측되는 것은 아니다.
터널 길이 전체의 누적 오차와 출구 GPS 재수신 시 점프를 측정하고, 불확실성 초과 시 감속/정지한다.
기본 경로 추종 성공 후 Stanley/MPC/EKF 등의 교체 필요성을 측정 결과로 판단한다.

## 6. 7명 작업 분담

| 담당 | 소유 범위 | 첫 산출물 | 이후 미션 책임 |
|---|---|---|---|
| 1 통신·송신 | 상태/충돌 파서, 제어 인코더, 모드 전환, watchdog | 패킷 명세표 + 저속 제어 왕복 확인 | 최종 명령 검사와 통신 장애 처리 |
| 2 센서·통합 | GPS/IMU/카메라/LiDAR 브리지, 실행 설정, 기록·재생 | 센서 토픽 + mock/replay 실행 + 지연 보고 | 통합 책임자, 성능·회귀 검증 |
| 3 위치 추정 | 좌표/TF, pose·속도 추정, 상태 품질 | GPS 정상 구간 odometry | 터널·재배치·GPS 복귀 |
| 4 카메라 | 신호·차선 인식 및 상태 출력 | 기록 영상 인식 결과 | 조도/안개/신호 연결 |
| 5 라이다 | 점군 전처리, 객체 검출·추적, 벽면 보정 | 객체·벽면 인터페이스 출력 | 장애물·보행자·끼어들기 관측 |
| 6 판단·계획 | 미션 제약 결합, 지역 경로, 속도 계획 | 기본 경로 전달 + 정지 제약 처리 | 회피/양보/동시 미션 |
| 7 제어·맵 | 공식 경로 전처리, 진행도, Pure Pursuit/PID | 경로 검증 + 기본 추종 | 정지 정확도·추종 성능 |

1·2는 통신 명세를 공동 검토하고, 2의 센서 범위가 밀리면 4·5가 각 센서 디코딩 검증을 지원한다.
7이 만든 맵/진행도 출력을 6이 사용한다. 5가 내는 터널 보정 후보는 3이 검증·융합한다.
담당 이름과 실제 숙련도에 따라 소유 범위를 조정하되 인터페이스 경계는 유지한다.

협업 규칙:

- 한 저장소, 담당 패키지별 작은 브랜치/PR. main에는 실행 가능한 기준 버전을 유지한다.
- 인터페이스 변경은 생산자·소비자가 함께 검토하고 문서·mock·재생 예제를 같이 갱신한다.
- 각 모듈은 고정 입력 예제, 정상 출력, 입력 끊김 동작, 실행 방법을 함께 제공한다.
- 모든 팀원은 첫날부터 mock으로 독립 작업한다. 실측 기록 확보 후 같은 기록으로 회귀 비교한다.
- 기준 기본 주행 설정과 대회 통합 설정을 분리하고 켜진 모듈/버전/파라미터를 매 실행 기록한다.
- 재생·mock 모드는 실제 UDP 제어 송신이 기본 차단되어야 한다.

예상 패키지: interfaces, morai_bridge, localization, map_route, perception_camera,
perception_lidar, planning, control, bringup, evaluation. 패키지 개수와 인원 수를 맞출 필요는 없다.

## 7. 단계별 완료 기준과 일정 산정

시작일·하드웨어·시뮬 접근 시간이 확인되지 않아 아래 기간은 견적이며 약속된 일정이 아니다.
통합 책임자가 단계 통과 결과를 기록한다. 뒤 단계의 독립 개발은 mock으로 먼저 진행한다.

| 단계 | 예상 작업일 | 완료 기준 |
|---|---|---|
| M0 계약 확정 | 1~2일 | 공식 경로/규정 대조, 환경·포트표·메시지·담당자 확정 |
| M1 통신/재생 | 2~3일 | 허용 센서와 상태 디코딩, 모드/기어 피드백 확인, 저속 출발·정지, 기록 재생 |
| M2 기본 주행 | 3~5일 | 정상 GPS 시험 구간 3회 연속 추종, 지정 정지, 재시작, 입력 만료 시 정지 동작 |
| M3 미션 통합 | 5~8일 | 신호/보행자 정지, 정적 회피, 동적 양보를 각각 재생 및 시뮬 검증 |
| M4 터널/전체 | 5~8일 | GPS 차단·복귀 및 터널 장애물 동시 처리, 전체 코스 반복 완주 |
| M5 제출 준비 | 마감 전 확보 | 제출 규칙에 따른 설정 동결, 실행 절차·실측 결과·최종 버전 기록 |

M2 측정 목표 초안: 제어 송신 20Hz 이상, 횡오차 p95 ≤0.5m, 직선 정속 오차 ≤2km/h,
정지 위치 오차 ≤0.5m. 이는 대회 공식 기준이 아니라 저속 기본 주행의 내부 출발점이다.
차량 외곽/바퀴가 차로 경계를 넘지 않는지 별도로 검사하며 평균 오차만으로 합격 처리하지 않는다.
정지선 기준점은 앞바퀴 등 공식 판정 기준과 차량 기준점 차이를 반영한다.
제어/센서 age의 p50/p95/max, 명령 간격 최대값과 deadline miss도 기록한다.
센서 송신 시각과 PC 시계 정합이 없으면 네트워크 편도 지연을 정확히 측정했다고 주장하지 않는다.
최종 만료시간·제동 여유·속도 상한은 실제 부하와 제동거리 측정으로 확정한다.

필수 장애 사례: 패킷 유실/잘림/역순, 오래된 영상, 상태 수신 단절, 계획 중단,
GPS 무효·고정값·음영·복귀, 경로 매칭 점프, 재배치, 빨간 신호+장애물 동시 발생, 터널 내 객체 등장.
GPS 음영 허용 모드에서도 위치 추정 health는 계속 검사한다.

9월 현장점검이 문서대로 예정되어 있다면 우선 확보할 것은 모든 미션 완성보다
포트/프로토콜 확정, 실부하 지연, 조향·제동 응답, 전체 허용 센서 기록이다. 실제 참가일 확인이 필요하다.

## 8. 사용자에게 필요한 정보

먼저 답변이 필요한 항목:

1. 알고리즘 PC 실제 IP, OS/ROS 버전, CPU/GPU/RAM, Python/C++ 선호, 사용할 기존 코드 유무.
2. 실제 제어 수신 포트와 허용 센서 목적지 포트, 현재 수신/송신 성공 범위, 현재 시뮬 빌드.
3. 공식 경로 TXT·규정 원본·최신 Q&A·샘플 시나리오 제공 가능 여부와 위치.
4. 7명 경험/희망 역할, 기본 주행 시연 목표일, 주당 작업 가능 시간, 시뮬 사용 가능 시간, 현장점검 참가일.

M1 이전 추가 확보:

- GPS/IMU/LiDAR 설정과 장착 pose, 제어 패킷 예제/명세, 허용 상태의 패킷 표본.
- 정지선·신호·차선 경계 데이터 제공 여부. 없으면 공식 지도/센서 관측을 바탕으로 수동 주석하고 검증할 작업을 M3에 포함한다.
- 대회 당일 IP/포트 설정 변경 허용 범위. 종합 문서의 '코드·파라미터 수정 불가'와 설정 분리 요구 사이의 실제 운영 절차 확인.
- '기본 주행 모델'을 학습 기반으로 의도했다면 데이터·학습 목표·추론 장비를 추가 확인해 해당 부분의 계획을 변경한다.

답변 이후 완료할 계획 확정 작업: 포트표와 실행 환경 고정 → 팀원 실명 배정 → 실제 날짜 일정화 →
메시지 상세 명세와 최초 구현 범위 확정. 그 전까지 위의 추천 구조로 독립적인 설계 작업은 가능하다.
