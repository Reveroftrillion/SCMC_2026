# 개인 Codex 개발 규칙

## 작업 체계

- 현재 팀명은 `CTRL`이다. 실행 패키지·자체 Python 모듈·실행 스크립트·launch는 `ctrl_*` 이름을 사용한다. ROS 토픽·노드명·파라미터·메시지 필드와 원본 작성자/URL/라이선스는 명명 정리와 구분해 보존한다. 이전 경로는 `ros1-port/tools/ctrl_name_map.json`으로 찾는다.

- 이 저장소는 개인이 Codex를 이용해 개발한다. 과거 3팀 역할 분담은 당시 이력이며 앞으로 작성할 계획의 현재 작업 체계로 가정하지 않는다.
- 현재 계획은 [DEVELOPMENT_WORKFLOW.md](ros1-port/docs/DEVELOPMENT_WORKFLOW.md), 문서 분류는 [MARKDOWN_INDEX.md](ros1-port/docs/MARKDOWN_INDEX.md)를 확인한다.
- 새 작업은 개발 목표, 영향 파일, 구현 방법, 검증 방법, 완료 기준으로 정리한다. 다음 세션이 바로 재현할 수 있는 명령과 판단 근거를 남긴다.

## 코드와 호환성

- 기존 동작을 변경하는 작업은 명시적으로 요청받았을 때만 수행한다. 리팩터링에 기능 수정이나 성능 최적화를 섞지 않는다.
- ROS 메시지와 필드, 토픽, 파라미터, YAML 키, launch 인자, 경로, 포트, 직렬화 및 공개 인터페이스 호환성을 우선한다.
- 기능 변경 없는 리팩터링은 최소 변경으로 진행한다. 내부 식별자 변경 시 참조를 모두 확인하고, 동적 참조의 안전성을 입증하지 못하면 해당 변경만 보류한다.
- 버그 수정은 원인과 재현 조건을 먼저 확인한다. 실패 경계를 확인하기 전에 threshold, ROI, 신호 기억, watchdog, 속도 제한을 바꾸지 않는다.
- `2026_CTRL_competition/`은 비교 기준으로 보존한다. 다른 RMT 구현으로 대체하거나 원본에서 테스트·캐시 생성을 하지 않는다.
- 코드와 문서의 실제 출처, 라이선스, 저작권, 작성자 정보를 보존한다.

## 검증과 기록

- 실험 기록과 과거 테스트 결과를 임의로 수정하지 않는다. 기존 검증 JSON, SHA256 manifest 및 날짜별 검증 문서는 근거 자료다.
- 테스트 통과를 위해 기대값·검사 기준·원본 모델·경로 해시를 변경하지 않는다. 의도된 식별자 불일치와 기능 회귀를 구분해 보고한다.
- 변경 후 가능한 구문 검사, 단위 테스트, 차등 비교, 문서 링크 검사를 실행하고 실패·skip·미실행 항목을 보고한다.
- Windows에서 실행하지 못한 ROS1/catkin/native 메시지/TF/MORAI 시험은 통과했다고 주장하지 않는다. 과거 Ubuntu 성공 기록은 수행 날짜와 범위를 명시한다.
- 실제 차량 제어 시험은 사용자의 명시적 지시 없이 수행하지 않는다. `drive:=true` 실행이나 제어를 송신하는 실험을 문서 정리·리팩터링의 일부로 실행하지 않는다.
- 현재 Windows 회귀 검사는 `ros1-port/.python310/python.exe ros1-port/tools/run_refactor_checks.py`를 사용한다. 결과는 매번 새 `verification/.work/identifier-refactor-*` 아래에 저장하며 기존 JSON을 덮어쓰는 검사를 직접 실행하지 않는다.
- 매 작업 완료 시 변경 파일, 작업 내용, 테스트 결과, 남은 문제와 확인하지 못한 호환성을 보고한다.

## Git

- 작업 시작 전 `git status --short`, `git branch --show-current`를 확인하고 사용자 변경을 보존한다.
- 현재 개발 기준은 `main`이다. ROS1 이식 기준은 과거 커밋 `c185c84024824fb5c2f4136e91a6b7b4e7bd02e7`로 확인한다. 병합 완료된 작업 브랜치는 정리했으며, 새 작업은 목적별 브랜치에서 진행하고 병합 후 삭제한다.
- 커밋 전 변경 범위와 `git diff --check`를 확인한다. 기존 파일의 whitespace 문제를 발견하면 이번 변경과 구분해 보고한다.
- GitHub push와 `main` 병합은 사용자의 별도 지시가 있어야 한다. 과거 작업의 push 승인을 새 작업에 적용하지 않는다.
- bag, build/devel/install, 다운로드 환경, 대용량 trace와 `docker/artifacts/`는 추적하지 않는다. 검증 요약과 재현 가능한 도구를 커밋 대상으로 검토한다.
