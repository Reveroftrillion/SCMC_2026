# 1. 왜 YOLO 로 가는가

`ctrl_camera/개발명세서.md` §7 의 미해결 항목이 전부 HSV 방식의 한계에서 나온다.

| §7 항목 | HSV 로 안 풀리는 이유 | YOLO 로 풀리는가 |
|---|---|---|
| 보행자 신호가 RED 로 잡힘 | 색만 보니 차량등·보행자등 구분 불가 | ✅ 클래스로 분리 학습 |
| LEFT 판정이 채움비 하나 | 화살표 모양을 안 봄 | ✅ 모양 학습 |
| Foggy / 13·15시 미검증 | 안개가 채도를 깎으면 임계값이 무너짐 | ✅ CNN 특징 + 램프 위치 단서 |
| 인식률이 곧 안전 | 임계값 튜닝의 한계 | ✅ 데이터로 개선 |

교체 지점은 `traffic_light_node.detect()` 하나다. 안정화·`Event.s`·게이트·UNKNOWN 발행은 인식 방법과 무관하므로 그대로 둔다.

# 2. 핵심 제약 — 물체가 작다

## 2-0. 카메라는 두 대다 (2026-09-22 변경)

| | 전방 카메라 | **자유 카메라** |
|---|---|---|
| 포트 | 9202 | **9208** |
| FOV | 90° (`fx = 640`) | **70° (`fx = 914`)** |
| 자세 | pitch 2° (전방) | **상향 — 신호등이 화면에 크게 들어오도록** |
| 쓰임 | 주행 파이프라인(기존), 근거리 백업 | **신호등 수집·학습·추론의 주력** |

**이 패키지가 다루는 건 자유 카메라다.** semantic(9210)도 자유 카메라와 **같은 pose·같은 FOV 70°·같은 해상도**로 달아야 한다 — 하나라도 다르면 마스크가 RGB 와 안 맞아 박스가 통째로 틀린다. §7 의 정렬 확인이 이걸 본다.

`tools/lidar_lane/morai_cam_udp.py:7-9` 의 카메라 모델(FOV 90°, fx 640)은 **전방 카메라 것**이라 그대로 두고, 이 문서의 계산은 자유 카메라 기준으로 다시 한다.

```
fx = (W/2) / tan(FOV/2) = 640 / tan(35°) = 914
픽셀 = 실제크기[m] × 914 / 거리[m]
```

## 2-1. 거리별 픽셀 크기 (자유 카메라, FOV 70°)

| 거리 | 램프 (0.3 m) | 사색등 함체 (≈1.2 × 0.35 m) | (참고) FOV 90° 였다면 함체 |
|---|---|---|---|
| 50 m | 5.5 px | 22 × 6.4 px | 15 × 4.5 px |
| 40 m | 6.9 px | 27 × 8.0 px | 19 × 5.6 px |
| 30 m | 9.1 px | 37 × 11 px | 26 × 7.5 px |
| 20 m | 13.7 px | 55 × 16 px | 38 × 11 px |
| 15 m | 18.3 px | 73 × 21 px | 51 × 15 px |
| **12 m** | **23 px** | 91 × 27 px | 64 × 19 px |

**검증 기준**: FOV 90° 전방 카메라에서 `ctrl_camera/개발명세서.md` §5 의 실측 "RED 램프 16×15 px" 가 12 m 계산값(16 px)과 일치했다. 같은 방식으로 자유 카메라도 실측 대조한다 — 12 m 에서 램프가 23 px 근처로 나와야 FOV 70° 가 맞는 것이다.

## 2-2. 여기서 따라오는 것

1. **여전히 함체를 잡는다.** 40 m 에서 램프는 6.9 px 로 P3(stride 8) 하한 근처지만, 함체는 27 px 다. 화각을 좁혀도 **함체가 램프의 4배**라는 비율은 그대로고, 그래서 라벨 단위(§3-1)는 안 바뀐다.

2. **검출 한계가 40 m 권으로 올라간다.** FOV 90° 기준 추정치가 25~30 m 였고 fx 가 `914/640 = 1.43` 배 커졌으니 단순 환산으로 **36~43 m**. `enter_distance_m = 40` 을 처음으로 실제로 덮는다. 30 km/h 제동거리 35 m 도 여유가 생긴다. **다만 이건 계산일 뿐이고, 실제 한계는 수집 데이터로 재는 것이 §7 의 마지막 항목이다.**

3. **ROI 를 다시 정해야 한다.** 기존 ROI(`x 0.15~0.85`, `y 0~0.41` = 896×295)는 **pitch 2° 전방 카메라**에서 신호등이 화면 위쪽 띠에 걸린다는 전제로 잡은 값이다. 자유 카메라는 위를 보므로 신호등이 화면 **중앙~중상단**으로 내려온다. 이 ROI 를 그대로 쓰면 신호등을 잘라먹는다.
   - `--check` 오버레이로 **신호등이 실제로 어느 y 대역에 오는지** 먼저 본다 (정지선 50/30/20/10 m 각 지점)
   - 그 대역에 여유를 붙여 ROI 를 정하고, **`imgsz` 는 ROI 의 긴 변에 맞춘다**(32 의 배수). 896 은 기존 ROI 에서 나온 수치일 뿐 목표가 아니다
   - 화각이 좁아져 신호등이 커졌으므로 ROI 를 넓게 잡아도 예전만큼 손해가 아니다. **"축소 없이 넣는다"** 는 원칙만 지키면 된다

4. **추론도 같은 카메라로 해야 한다.** 자유 카메라로 학습한 모델은 자유 카메라 그림만 본다. 대회 때 `traffic_light_node` 의 입력을 전방(9202)에서 자유 카메라로 바꿔야 하고, **FOV·해상도·자세가 수집 때와 한 글자도 달라선 안 된다.** §8 참고.

# 3. 결정과 근거

## 3-1. 라벨 단위 — 함체 1박스 + 상태 클래스

```
클래스 6개   red   yellow   green   green_left   left   pedestrian
```

함체 하나에 박스 하나, 클래스가 곧 신호 상태다.

**왜 램프 단위가 아닌가.** 램프는 40 m 에서 4.8 px 라 P3(stride 8) 검출 하한 아래다. 함체는 4배 크다. 또 함체 박스 안에는 **어느 위치의 램프가 켜졌는지**가 들어 있어, 한국 사색등의 고정 순서(`적-황-좌-녹`)를 위치 단서로 학습할 수 있다. 안개로 채도가 날아가도 위치는 남는다.

**왜 함체만 잡고 색은 HSV 가 아닌가.** 그러면 §7 의 Foggy 취약성과 LEFT 채움비 문제가 그대로 남는다. 해결하려던 문제가 안 풀린다.

**되돌릴 구석.** 이 라벨은 상위집합이다. 나중에 "함체만 검출 + 색은 따로" 방식으로 바꿔도 클래스만 무시하면 그대로 쓴다.

**매핑** (`detect()` 반환값)
| 클래스 | Event value | 비고 |
|---|---|---|
| `red` | `RED` | |
| `yellow` | `YELLOW` | 대회엔 없다지만(2026-09-17) 보이면 라벨은 단다 |
| `green` | `GREEN` | |
| `green_left` | `GREEN` | 직좌 = 직진 가능. 별도 값으로 내면 `go_colors` 에 안 걸려 헛정지한다 |
| `left` | `LEFT` | `stop_line_node` 가 "뜻 모르는 색" → 정지 |
| `pedestrian` | — | **색 판정에서 제외.** 라벨은 달되 결과에서 버린다 |

`pedestrian` 을 배경으로 두지 않고 클래스로 두는 이유: "이건 차량등이 아니다"를 명시적으로 가르치는 쪽이 훨씬 강한 지도다. §7 1번이 여기서 해결된다.

## 3-2. 라벨 생성 — semantic 카메라

카메라 2대를 같은 위치에 달아 하나는 RGB, 하나는 semantic 으로 받는다. semantic 의 신호등 클래스 색(분홍) 마스크에 연결요소를 돌리면 **픽셀 단위로 정확한 박스**가 공짜로 나온다.

**COCO 사전학습은 안 쓴다.** COCO 는 실사로 학습된 모델이라 Foggy·야간·원거리에서 약한데, 하필 그게 §7 에서 미검증으로 남은 구간이다. COCO 가 놓친 프레임은 라벨이 안 생기고, 결국 **학습 데이터가 쉬운 프레임 쪽으로 편향**된다. 게다가 COCO 박스는 느슨하고 semantic 박스는 타이트해서, 섞으면 박스 규약이 흔들린다.

## 3-3. 상태 판정 — 박스 안 HSV + 위치 검증

semantic 은 **어디**만 알려주고 **무슨 색**인지는 안 알려준다. 박스 안에서 기존 HSV 를 돌려 상태를 정한다.

**박스 안은 배경이 없다.** 지금 HSV 가 어려운 건 화면 전체를 뒤져서 풀이 노랗게 잡히고 후미등이 빨갛게 새기 때문이다. 함체 안에는 켜진 램프 말고 채도 높은 게 없으므로 `s_lo`/`v_lo`/`min_fill_ratio` 를 크게 낮춰도 오탐이 없다. 안개 프레임도 임계값만 내리면 잡힌다.

**위치 검증.** 켜진 덩어리의 정규화 x 위치로 교차확인한다.
```
사색등   red 0.125 │ yellow 0.375 │ left 0.625 │ green 0.875
삼색등   red 0.17  │ yellow 0.50  │            │ green 0.83
```
색과 위치가 어긋나면 **검수행**으로 보낸다. 2000장 중 5~10% 면 검수는 30분이면 끝난다.

**뒷면 신호등 제거.** 다른 방향을 보는 신호등도 semantic 에선 같은 분홍이다. 박스 안에서 램프를 못 찾으면 뒷면이거나 소등이므로 **데이터셋에서 제외**한다. HSV 판정이 이 필터를 겸한다.

**보행자등 분리.** semantic 이 차량등과 보행자등을 같은 클래스로 묶을 가능성이 높다(확인 필요). 묶여 있어도 **종횡비로 갈린다** — 차량등 3:1~4:1, 보행자등 1:2.

**덩어리 병합.** 한 갠트리의 신호등 여러 개가 연결요소 하나로 붙을 수 있다. 8:1 처럼 비정상적으로 긴 박스는 병합 의심으로 검수행.

## 3-4. TrafficLight Status — 라벨 출처가 아니라 검수 신호

주행 중엔 금지 채널이지만 **학습 데이터 생성에는 써도 된다** (2026-09-20 확인). 그래도 라벨 출처로는 안 쓴다.

**이유 1 — 라벨은 픽셀을 설명해야 한다.** 전환 순간이나 렌더링이 어긋난 프레임에서 Status 는 GREEN 이라고 하는데 화면엔 초록이 없을 수 있다. 거기 GREEN 을 붙이면 **"초록이 안 보여도 초록이라고 답하라"** 를 가르치는 셈이다. 가장 위험한 실패(자신 있게 틀린 GREEN)를 데이터로 주입하게 된다. HSV 로 읽으면 라벨이 정의상 픽셀과 일치한다.

**이유 2 — 박스마다 상태가 필요하다.** 한 프레임에 신호등이 5개 넘게 보인다. YOLO 는 모든 박스에 라벨이 있어야 한다(없으면 "여긴 신호등이 아니다"로 학습된다). Status 는 잘해야 자차 관련 하나를 준다. 나머지는 어차피 HSV 로 읽어야 하므로 **일이 줄지 않고 라벨 출처만 둘로 갈린다.**

**쓰는 방법.** HSV 라벨러의 **체계적 실수**(직좌를 전부 GREEN 으로 뭉갠다, 특정 모델에서 한 칸씩 밀려 읽는다)는 자기 자신과 비교해선 안 드러난다. 자차 신호등 하나만이라도 독립적인 정답과 대조하면 바로 보인다. 불일치율이 튀는 구간만 들여다본다.

**뒤집힐 조건.** Status 가 **신호등 ID별**로 상태를 주고 MGeo 에서 그 ID 의 3D 좌표를 얻을 수 있으면, `PinholeCamera`(`tools/lidar_lane/morai_cam_udp.py:78`)로 투영해 박스와 ID 를 짝지을 수 있다. 그 경우에도 이유 1 은 남으므로 **HSV 로 읽고 ID 로 검증**하는 구조는 유지하되, 검수 대상이 전체 박스로 넓어져 품질 보증이 촘촘해진다.

## 3-5. 수집 정책 — 전부 녹화하지 않는다

**시뮬이라 같은 상황을 다시 만들기 쉽다.** 실차 수집은 그 순간을 다시 못 얻으니 전부 녹화해 보험으로 쌓지만, 시뮬은 다시 돌리면 된다. 그러면 raw 를 쌓는 가치가 거의 0 이고, 목표가 **양이 아니라 다양성**이 된다.

**정지선 근접 필터는 이 코스에서 무의미하다.** 전역경로 정지선 s 가 65.7, 153.5, 202.5, 306.1, 431.0, 541.3, 599.2, 879.3, 924.1 로 간격이 45~280 m(대부분 100 m 안팎)이다. 랩 960 m 에서 "120 m 이내"로 거르면 **90%가 남는다.** 거르는 게 아니다.

**실제로 줄이는 건 거리 샘플링이다.**
```
20 Hz 연속        랩당 3500장
2 m 마다          랩당  480장   ← 87% 감소
6개 조건          총  2880장    ← 목표치
```

```
저장 규칙
  주행 중    2 m 이동마다
  정차 중    2 s 마다        ← 적색→녹색 전환 순간을 놓치지 않으려고
  근접 필터  없음
  meta 에 s 기록            ← 정지선 거리는 extract 에서 오프라인 계산
```

`StopLineTable` 은 수집 때 필요 없다. `/localization/s` 로 "2 m 움직였나"만 보면 된다.

## 3-6. 중복 제거 — 프레임이 아니라 라벨로

가장 심한 중복은 **빨간불 정차 구간**이다. 차도 안 움직이고 신호도 그대로라 프레임이 사실상 동일하다. 그런데 그 구간 끝의 **전환 순간은 가장 값진 데이터**(`go_confirm_s` 가 동작하는 장면)라 통째로 버릴 수 없다.

그래서 `ctrl_extract.py` 가 만든 라벨로 판정한다.
```
라벨 서명 = 정렬된 [(박스 중심 격자화, 크기 구간, 클래스)]
직전에 남긴 프레임과 서명이 같으면 버린다
```
차가 안 움직이고 신호도 그대로면 서명이 같다 → 버린다. 신호가 바뀌면 → 남긴다. 크기 구간이 바뀌면 → 남긴다. **중복을 픽셀이 아니라 "모델이 배울 내용"으로 재는 것.** 추가 작업이 없다(어차피 만들 `ctrl_extract.py` 출력만 쓴다).

## 3-7. 카메라 타임스탬프 — `camera_bridge` 에 `stamp_source` 추가

`camera_bridge` 가 MORAI 타임스탬프를 버리고 수신 시각으로 찍는다(`ctrl_camera_bridge.py:119`). 헤더에 `sec`/`nsec` 가 있는데 offset 15 의 `size` 만 읽는다.

```
'MOR'  sec   nsec  index  size   JPEG
0-2    3-6   7-10  11-14  15-18  19-
        └─ 안 읽음        └─ 읽음
```

**지터 자체는 문제가 아니다.** semantic 은 단색이라 JPEG 가 작게 압축돼 먼저 도착하지만 몇 ms 수준이고, 20 km/h 에서 3 ms = 1.7 cm, 20 m 거리 물체에선 0.5 px 다.

**진짜 위험은 한 프레임씩 밀려 짝지어지는 것.** 조각 유실로 한쪽 프레임이 버려지면 그 뒤로 짝이 밀린다. 50 ms = 0.28 m 이동 = 20 m 거리에서 **9 px**. 이 라벨은 조용히 틀린다.

MORAI 스탬프로 맞추면 같은 시뮬 프레임끼리만 묶여 이 위험이 사라진다. `stamp_source: recv|morai`, **기본 `recv` 라 주행 파이프라인은 무변경**. 수집 launch 에서만 `morai` 로 켠다.

downstream 확인: 카메라 `header.stamp` 를 쓰는 곳이 없다. `traffic_light_node.on_image` 는 `get_clock().now()` 로 자체 계산하고(`traffic_light_node.py:163`), `camera_view` 도 안 쓴다. 켜도 깨질 데가 없다.

**대회 패키지에 들어가는 변경은 이것 하나뿐이고, `semantic` 이라는 단어조차 안 들어간다.**

## 3-8. 수동 보정 — Roboflow 왕복

`ctrl_extract.py` 의 자동 라벨은 완벽하지 않다. 검수행(색↔위치 불일치, 병합 의심)과 semantic 이 놓친 원거리 함체는 **사람이 손으로 고쳐야** 한다. 그 도구로 Roboflow 를 쓴다.

**규격은 이미 맞는다.** Roboflow 가 읽고 쓰는 `YOLOv8 PyTorch TXT` 는 `images/` + `labels/*.txt` + `data.yaml` 이고, txt 한 줄이 `class_id cx cy w h`(0~1 정규화)다. `write_yolo()` 가 만들 것과 같은 형식이라 **변환 코드가 필요 없다.**

**다만 Roboflow 를 데이터셋의 주인으로 삼지 않는다.** 라벨 편집기로만 쓰고, 분할·중복제거·통계는 이쪽에서 한다. 이유는 아래 ①②.

```
ctrl_extract.py ──(업로드)──► Roboflow ──(Export YOLOv8)──► import_roboflow.py ──► dataset/
   자동 라벨              손으로 보정                     재분할·재중복제거
```

### 규격을 맞추려고 지켜야 할 5가지

**① 분할을 Roboflow 에 맡기지 않는다.** Roboflow 의 기본 동작은 train/valid/test 재분할이고, 그건 **프레임 단위 무작위**다. §5 에서 금지한 바로 그것 — 연속 프레임이 양쪽에 쌍둥이로 들어가 mAP 가 부풀려진다. 업로드는 전부 `train` 으로 밀어넣고, 내려받은 뒤 `split_by_group()` 으로 (조건, 정지선) 단위 분할을 다시 한다.

**② Version 생성 시 Preprocessing / Augmentation 을 전부 끈다.** Roboflow 는 기본으로 `Auto-Orient` + `Resize 640×640 (stretch)` 를 건다. ROI 는 정사각이 아니라 가로로 긴 띠라 가로세로비가 뭉개지고 램프가 더 작아진다. **Resize: None.** 증강도 ultralytics 쪽에서 하므로 전부 끈다 — 특히 `Flip Horizontal` 은 §5 의 `fliplr=0.0` 금지와 정확히 같은 이유로 **치명적**이다(좌회전 화살표가 뒤집힌다).

**③ 클래스 순서를 하드코딩하지 않는다.** Export 시 `data.yaml` 의 `names` 순서가 이쪽 `CLASSES` 튜플 순서와 **달라질 수 있다**(알파벳 정렬). `red=0` 을 코드에 박아두면 라벨이 통째로 어긋나는데 에러는 안 난다. `ctrl_train.py` / `ctrl_evaluate.py` 는 **항상 `data.yaml` 의 `names` 를 읽어서** 인덱스↔이름을 정한다. 왕복 후 `check_dataset()` 이 순서를 찍어 확인한다.

**④ 파일 이름에 `tag` 와 `s` 를 박아 올린다.** Roboflow export 는 파일명을 `000123_jpg.rf.<hash>.jpg` 로 바꾼다. 원본 이름은 **앞쪽에 남으므로** 거기에 정보를 넣어두면 `meta.csv` 로 되돌아갈 수 있다. §6 의 거리 구간별 혼동행렬이 `s` 를 필요로 하므로 이 연결이 끊기면 평가가 안 된다.
```
업로드 파일명   sunny_11h_000123_s0412.3.jpg
export 후       sunny_11h_000123_s0412.3_jpg.rf.9ab3....jpg
                └──────── 여기서 파싱 ────────┘
```

**⑤ 전체 프레임이 아니라 ROI 크롭을 올린다.** 1280×720 에서 27×8 px 박스를 손으로 그리는 건 고통스럽다. ROI 크롭이면 화면을 꽉 채워 보이고, **학습에 들어가는 것과 같은 그림**이라 눈으로 본 것이 곧 모델이 볼 것이 된다. 크롭은 `ctrl_extract.py` 가 하고 박스 좌표도 크롭 기준으로 쓴다.

### 확인할 것
- Roboflow 무료 플랜은 프로젝트가 **공개(Universe)** 로 열린다. 대회 데이터를 올려도 되는지 판단하고, 아니면 유료 플랜이나 로컬 CVAT 을 쓴다
- 위 ①~③의 기본값은 UI 버전에 따라 다를 수 있다. **첫 왕복 때 50장으로 시험**해서 내려받은 결과가 올린 것과 같은지(클래스 순서, 해상도, 박스 좌표) 확인한 뒤 본 작업을 한다

# 5. 학습 설정 — 반드시 바꿔야 하는 것

ultralytics 기본값을 그냥 쓰면 이 문제에서 망가진다.

| 설정 | 기본 | 바꿀 값 | 이유 |
|---|---|---|---|
| `fliplr` | 0.5 | **0.0** | **좌회전 화살표가 우회전이 된다.** 사색등 `적-황-좌-녹` 이 `녹-좌-황-적` 으로 뒤집혀 위치 단서를 정반대로 학습한다. 가장 위험한 기본값 |
| `hsv_h` | 0.015 | **0.0** | 색상이 곧 클래스다. 흔들 이유가 없다 |
| `scale` | 0.5 | **0.25** | 이미 작은 물체를 절반까지 줄이면 학습이 깨진다 |
| `hsv_s` | 0.7 | 유지 | 안개가 채도를 떨어뜨린다 → 일반화에 직접 도움 |
| `hsv_v` | 0.4 | 유지 | 시간대(11/13/15시) 변화 |
| `imgsz` | 640 | **ROI 긴 변 (32 배수)** | ROI 를 축소 없이. 자유 카메라 ROI 확정 후 결정 (§2-2 3번) |

**val 분할을 무작위로 하면 안 된다.** 접근 중 연속 프레임은 거의 같은 그림이라, 무작위 분할하면 train/val 에 쌍둥이가 나뉘어 들어간다. mAP 가 0.99 로 나오고 실주행에서 무너진다. **(조건, 정지선) 단위로 통째로** 나눈다. `meta.csv` 의 조건 태그가 이걸 위해 있다.

학습 규모: YOLO26s, ~2900장, `imgsz` = ROI 긴 변, `batch=8`(8 GB, imgsz 커지면 줄인다), `epochs=100~150`, `patience=30`, COCO 가중치에서 전이학습.

> `yolo26s.pt` 가 설치된 ultralytics(8.4.156)에서 실제로 받아지는지 첫 학습 전에 확인할 것. 안 되면 버전을 올린다.
